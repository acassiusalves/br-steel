# BR Steel MCP OAuth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Delegação somente se autorizada para a execução.

**Goal:** Conectar o Claude pessoal de cada usuário por OAuth e habilitar leitura e escrita autorizadas em vendas, estoque e produção.

**Architecture:** Supabase dedicado fornece OAuth; Next.js hospeda `/api/mcp`, consentimento e serviços autorizados. Firestore permanece como banco operacional. Interface web e MCP compartilham regras de negócio, idempotência e auditoria.

**Tech Stack:** Next.js App Router, TypeScript, SDK oficial MCP, Firebase Admin/Firestore, Supabase Auth, JOSE e Zod. Testes de domínio com Vitest e integração com emulador Firestore e Supabase de teste.

**Spec:** [Arquitetura e análise do Calculaqui](../specs/2026-09-11-mcp-oauth-design.md).

## Global Constraints

- Status: etapa 1 implementada e validada localmente em 11/09/2026; etapas 2–7 pendentes. Ver [registro da etapa 1](../../mcp-etapa-1.md).
- Prioridade confirmada pelo usuário: vendas, estoque e produção.
- Node.js 22+; fixar versões exatas das dependências adicionadas e manter lockfile.
- Firestore permanece como banco operacional; não reutilizar projeto/credenciais do Calculaqui.
- Identidade primária: ID persistente de `users`; identidade OAuth: `sub` vinculado no backend.
- Nenhuma credencial Anthropic exigida; nenhuma chamada de modelo necessária no caminho MCP.
- Capacidades: `vendas:read`, `vendas:sync`, `estoque:read`, `insumos:read`, `insumos:write`, `producao:read`, `producao:write`.
- `MCP_ENABLED=false` e `MCP_WRITES_ENABLED=false` por padrão.
- Consultas: padrão 50, máximo 100 registros; corpo 64 KiB; saída 256 KiB.
- Datas civis em `America/Sao_Paulo`; timestamps em ISO UTC.
- Prévia de escrita: 10 minutos; access token alvo: 15 minutos.
- Auditoria: 90 dias; idempotência: 24 horas; limpeza por TTL.
- Limites: 60 leituras e 10 confirmações/minuto por usuário+cliente; 2 sincronizações simultâneas por instalação.
- Sem escrita em produção durante testes; não fechar regras de coleção antes de migrar consumidores legítimos.

## Etapa 2 — Provar OAuth com o login atual

**Criar:** arquivos `src/server/oauth/`, rotas `mcp-auth`, página de consentimento, configuração Supabase, hook de audiência e `tests/oauth/{identity-bridge,consent,grants}.test.ts`.

**Modificar:** `src/app/login/page.tsx`, `src/app/perfil/page.tsx`, login/logout e configuração de ambiente documentada.

**Interfaces:** a ponte recebe `Request` e `authorization_id`, resolve o usuário pelo cookie e devolve sessão por Set-Cookie; o cliente recebe somente resultado/status. `getAuthorizationDetails` fornece cliente e redirect verdadeiros. Concessões são identificadas por hash de `sub + client_id`, nunca por um identificador escolhido livremente pelo navegador.

- [ ] Escrever testes com adaptador Supabase simulado: UID/e-mail no corpo são ignorados; colisão de vínculo falha; sessão Supabase de outra conta é descartada; CSRF e return URL externo são recusados; OTP não aparece no JSON.
- [ ] Executar testes e confirmar falhas antes da implementação.
- [ ] Implementar provisionamento/vinculação única, geração/consumo de OTP no backend, cookies próprios e preservação de `authorization_id` no login e troca de senha.
- [ ] Implementar consentimento com capacidades reais, persistência `pending → active` e rollback de falha. Não reutilizar consentimento OAuth antigo para ampliar capacidades locais sem nova decisão.
- [ ] Implementar revogação local primeiro e revogação no Supabase depois. Reautorização da mesma concessão aguarda resolução de revogação pendente; validar `iat` contra `validAfter` sem reabilitar tokens antigos.
- [ ] Criar projeto/ambiente Supabase dedicado de teste na execução, habilitar OAuth/DCR, configurar site/consentimento e assinatura assimétrica. Usar Node.js 22+ e versões exatas das bibliotecas adicionadas.
- [ ] Hook de audiência distingue token OAuth de sessão comum; configura audiência MCP em autorização e refresh. Usar o formato do hook documentado para a versão adotada.
- [ ] Executar fluxo com cliente OAuth de teste: descoberta → DCR → PKCE → login → consentimento → código → token → refresh → revoke. Validar PKCE errado e redirect diferente.

**Aceite:** tokens OAuth individuais trazem `sub`, `client_id` e audiência MCP; token de outro recurso falha. Após revogar e reconectar, access e refresh tokens anteriores permanecem inutilizáveis. Guardar somente evidência sanitizada.

**Configuração necessária na execução:** `APP_ORIGIN`, `MCP_PUBLIC_URL`, `SUPABASE_URL`, chave pública e chave secreta de servidor, `AUTH_SESSION_SECRET`, credencial Admin Firebase já gerenciada pelo ambiente. Valores reais não entram em arquivos versionados. Não escolher nem criar recursos de produção nesta etapa.

## Etapa 5 — Escrita local com prévia, auditoria e idempotência

**Criar:** `src/server/mcp/{previews,idempotency}.ts`, ferramentas de escrita de insumos/produção e `tests/mcp/{write-tools,concurrency}.test.ts`.

**Modificar:** serviços de insumos/produção, tipos de auditoria e `firestore.rules`. Todas as coleções MCP novas ficam sem acesso direto do navegador.

**Contrato de prévia e confirmação:**

```ts
type Preview = {
  operation_id: string;
  expires_at: string;
  status: 'preview';
  changes: Array<{ entityId: string; before: unknown; after: unknown }>;
  warnings: string[];
};
type Confirmation = {
  operation_id: string;
  idempotency_key: string;
  confirmar: true;
};
```

O payload de negócio fica no servidor. A confirmação não permite trocar SKU, lote, quantidade ou usuário; a ferramenta verifica que a prévia corresponde à operação chamada.

- [ ] Testar prévia sem mutação, expiração, outro usuário/cliente, versão de registro alterada e flag de escrita desligada entre prévia e confirmação.
- [ ] Testar entrada/saída com quantidade inválida; saldo negativo permitido com alerta; mínimo maior que máximo recusado.
- [ ] Testar criação de lote com pedido/SKU inexistente, responsável inválido e dois criadores concorrentes gerando números distintos.
- [ ] Executar testes e confirmar falhas; implementar transações com checagem de versão, idempotência e auditoria juntas. ID do evento deriva da operação para evitar duplicação.
- [ ] Testar duas confirmações simultâneas com a mesma chave: exatamente um movimento/efeito. Chave repetida com outro payload deve retornar conflito.
- [ ] Simular falha no registro de auditoria: transação inteira aborta. Repetir com sucesso e confirmar evento atribuído ao usuário autenticado, `source=mcp` e client ID.
- [ ] Habilitar escrita para usuário de teste; executar movimentação local e criação/movimento de lote pelo Claude; conferir alteração nas telas e no histórico.

**Aceite:** uma solicitação repetida não muda o saldo duas vezes; prévia não altera negócio; autoria não pode ser forjada. `confirmar=true` não é descrito como prova técnica de aprovação humana.

## Questões operacionais para a execução

O desenho adota projeto Supabase dedicado e domínio público atual do BR Steel. Os identificadores e valores reais serão obtidos do ambiente ao executar, antes de qualquer implantação. Não há URL de produção confirmada nesta análise.

Permissões de escrita propostas e fronteira entre estoque local e estoque Bling estão explícitas na spec para revisão do produto. Mudar saldo no Bling ou criar/cancelar venda no ERP exige acrescentar operações específicas, conferir a API oficial e testar os efeitos externos antes de habilitar essas ferramentas.
