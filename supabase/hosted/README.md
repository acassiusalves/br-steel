## Inspeção antes da aplicação

1. Executar `inventory.sql` como `postgres` no projeto selecionado. É um único `SELECT` de catálogos, sem leitura de dados de usuários ou segredos. Conferir identidade do projeto no dashboard ou no argumento explícito da CLI: o nome do banco não comprova o projeto.
2. Revisar os objetos existentes em `public` e `private`, proprietários, permissões, permissões padrão e definição/dependências de um eventual `private.mcp_access_token_hook(jsonb)`. Guardar antes da aplicação a definição e ACL da função, além do proprietário e ACL do schema `private` (campo `schemas` do inventário), para recuperação. Se o schema não existir, registrar explicitamente essa ausência. A ausência de dependências em `pg_depend` não comprova ausência de uso pelo Auth: a referência do hook é configuração externa ao banco.
3. No dashboard, inspecionar o hook atual de Custom Access Token, usuários de teste, clientes OAuth e aplicações que já usam o projeto. O hook proposto altera `aud` para **todo token com `claims.client_id` não vazio**, incluindo refresh. Se o projeto já emitir OAuth para outro recurso, avaliar essa dependência antes de aplicar a política global. Sessões sem esse claim conservam todos os claims e a audiência anterior.
4. Conferir os schemas expostos pela Data API no dashboard; `private` deve permanecer fora dessa lista. A consulta mostra a configuração de sessão `pgrst.db_schemas` quando disponível, mas um valor nulo não comprova a configuração do serviço. Inspecionar o histórico de migrations e os registros OAuth usando as colunas retornadas pelo inventário. Não selecionar segredos de clientes ou tokens para registrar evidências.

A presença de tabelas em `public` ou `private` não é tratada como erro: configurações legítimas do provedor podem exigir objetos. A migration não cria nem modifica tabelas, usuários, clientes OAuth ou configuração Auth.

## Recuperação

A transação do teste direto é revertida automaticamente; a verificação CLI não faz escritas persistentes. Para reverter uma aplicação já confirmada, restaurar a seleção/configuração anterior do hook no Auth e, caso uma função existente tenha sido substituída, restaurar sua definição e seus grants inventariados. Se a função tiver sido criada nesta aplicação, removê-la apenas após retirar sua referência do Auth.

Restaurar também qualquer ACL do schema `private` alterada pela migration, incluindo `USAGE` concedido a `supabase_auth_admin`. Usar o proprietário e a ACL registrados **antes da aplicação** como referência; antes da reversão, capturar novamente a ACL atual para identificar mudanças posteriores legítimas e restaurar apenas as alterações desta migration. Um schema que não existia deve permanecer identificado assim no inventário anterior. Não apagar o schema `private` nem seus objetos automaticamente, nem revogar acesso de consumidores adicionados depois: podem pertencer a usos legítimos. Se não houver inventário anterior, reconstruir as permissões antes de tentar restaurá-las; não presumir os grants.

Tokens já emitidos não são revertidos por alterar o hook; a validação/revogação de sessões do piloto pertence à verificação operacional.
